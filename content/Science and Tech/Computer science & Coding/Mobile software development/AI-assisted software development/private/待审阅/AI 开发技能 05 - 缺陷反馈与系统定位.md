# AI 开发技能 05 - 缺陷反馈与系统定位

整理日期：2026-11-28｜状态：待审阅

入口：[[AI 辅助软件开发 - Workflow 总览]]｜案例：[[Knowledge Map 1.0.0 - AI 辅助开发复盘]]

==把一次异常保存为可以检查的触发序列，再用证据缩小原因。==

## 本次项目里的例子

第一条反馈是：iPad 上传、PC 下载后，已打开画布没有马上变化，重开标签后才更新。后一次成功并没有抹掉首次异常。

技术复现发现：范围外说明笔记会推进全局失效标记，但图谱监听器没有安排相应重建，当前图谱因而被判为过期。这个缺陷与现象相符；首次异常缺少完整事件轨迹，所以记录没有将它认定为当次唯一根因。

后来用户按复验步骤操作，旧 iPad 候选又出现拖动回弹和 `unified-graph-unavailable`。组合验证表明同一过期门禁也影响本机保存。两端统一修复候选后，再分别验证保存和接收更新。

## 下次怎样反馈

保留能帮助定位的信息：设备和版本、候选来源、起始状态、操作顺序、实际与期望表现、错误原文、是否手动重建或重启。

如果操作可能改变证据，先保存允许保留的现场，再决定后续动作。需要发送文件时，限定范围；账号配置和真实私有资料要单独处理。

## 一个可复用的定位循环

1. 记录现象，先区分观察、推测和待验证问题。
2. 核对实际运行候选，避免把不同版本的行为混在一起。
3. 建立足够小的复现输入，保留触发缺陷所需的步骤。
4. 提出可检验的假设，一次改动围绕一个主要原因。
5. 对比旧版与修复版：断言应能区分错误和正确行为。
6. 执行受影响回归，再安排真实使用流程复验。

旧版按预期触发错误，也可能让测试脚本以成功码结束；要读断言含义，不能只看退出码。

## 可以复制的反馈与提问模板

```text
设备/系统/应用/插件版本：……
候选来源或文件摘要：……
起始状态与操作顺序：……
实际表现及错误原文：……
期望表现：……
额外干预：是否重开、重建、重复同步？
复现次数与可保留的证据：……
请先区分已知事实、候选原因和缺失证据，再提出最小复现与验证办法。
```

## 小练习：给异常写一张反馈卡

用一个合成例子写反馈，例如“下载后文件已到达，但画布未更新”。列出至少两个可能原因，以及各自需要什么证据才能排除。

- [ ] 能复述不依赖猜测的实际经过。
- [ ] 能说明哪一步可能改变现场。
- [ ] 能设计区分“最终一致”和“自动更新”的观察。
- [ ] 修复结论没有超出已验证的范围。

## 适用边界

重启后恢复可以作为线索，但还需要验证缺陷是否消失。发现一个真实缺陷，也需要检查它与历史现象的因果关系。工具启动或权限失败应记录为工具问题，不能直接记成产品故障或产品通过。
