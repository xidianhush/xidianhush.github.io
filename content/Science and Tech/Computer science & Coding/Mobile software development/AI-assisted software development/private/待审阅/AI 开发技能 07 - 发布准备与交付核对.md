## 本次项目里的例子

Knowledge Map 1.0.0 冻结了 `main.js`、`manifest.json`、`styles.css` 三份运行文件，核对本地构建、PC 实际安装、iPad 回传文件和远端下载的字节。仅显示 v1.0.0 的截图没有承担全部验证责任。

正式流程还区分了手动演练、合并、tag、GitHub Release 和社区审核。用户明确确认发布后才执行相应动作，随后回读资产及社区状态。

本项目使用 `1.0.0` 形式的 tag。运行文件白名单和 tag 约定需要按各项目核对。

## 下次怎样准备发布

1. 确定要发布的源码状态和用户已接受的产品范围。
2. 核对版本声明、依赖锁、构建与打包入口。
3. 执行项目要求的检查；干净导出验证是否依赖未提交或私有现场。
4. 建立运行文件清单与摘要，并核对实际安装内容。
5. 审阅拟公开差异、文档、截图和包内容，再推送。
6. 根据现有明确授权执行正式发布；成功后下载或回读结果。
7. 分别记录代码托管发布和插件目录状态，以及未完成项。

压缩包的压缩方式不同可能导致 ZIP 摘要不同。核对实际交付字节时，应比较成员清单及其中的运行文件。

## 隐私与授权也属于交付

本次有旧归档文档中的机器路径在复核完成前被推送，后续普通提交做了脱敏并扩大检查范围。旧历史仍可能可检索，不能把修改当前文件说成清除了历史。

已有授权应被准确沿用；准备演练、源码推送、正式发布和历史改写的范围需要分别确认。可以把这一点写进当前清单，减少重复询问与误操作。

## 可以复制的提问模板

```text
请先准备可审阅的发布候选：来源提交、运行文件清单、版本一致性、检查结果及已知边界。
核对实际安装与候选字节，审阅拟公开内容和最终包。
区分本地构建、演练、远端CI、正式发布、目录审核的状态。
执行已明确授权的步骤；需要新决定时提供具体结果与原因。
完成后回读实际资产，记录精确来源、验证范围和未完成事项。
```

## 小练习：写一份交付说明

为一个合成小项目写说明，回答：交付哪个提交？包含哪些文件？验证了什么？谁确认体验？怎样回退？哪些还没测？

- [ ] 能解释版本号和文件摘要各证明什么。
- [ ] 能区分演练成功和正式发布成功。
- [ ] 能指出一项公开前需要检查的内容。
- [ ] 能说明一个仍然存在的边界。

## 适用边界

哈希帮助核对字节，不等于加密、安全认证或用户体验通过。两位独立新用户试用在本次由用户明确后置，没有记为完成；Android、iPhone 等未验证范围继续披露。
