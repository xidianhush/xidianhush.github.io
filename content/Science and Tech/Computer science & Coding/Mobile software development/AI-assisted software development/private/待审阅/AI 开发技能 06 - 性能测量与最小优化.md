# AI 开发技能 06 - 性能测量与最小优化

整理日期：2026-11-28｜状态：待审阅

入口：[[AI 辅助软件开发 - Workflow 总览]]｜案例：[[Knowledge Map 1.0.0 - AI 辅助开发复盘]]

==先规定测量条件并定位主要耗时，再选择能保持行为的最小改动。==

## 本次项目里的例子

G4 围绕较大历史样本做有界测量，进一步区分宿主构造、历史校验和布局投影等阶段。后续定位到重复材料读取，首批优化集中在已有会话缓存。

固定 406 操作样本中，三组前后交替的 Node 对照，宿主构造中位数由 34.470 秒降至 18.917 秒，约减少 45.1%。接受的历史、快照和状态深比较一致。

这是指定样本、驱动和环境下的收益。它没有直接测量 iPad 或真实 IndexedDB，也不能与另一轮不同驱动的旧绝对时长拼成收益曲线。

## 下次怎样测量

1. 定义慢的场景：什么操作、什么规模、用户在哪里等待。
2. 确定计时起止点、调查上限和必要的状态保护。
3. 固定输入、候选、环境与驱动，保留原始数据。
4. 分解阶段，并结合调用或读取计数寻找重复工作。
5. 让前后候选只在目标改动上不同，安排多次交替运行。
6. 同时核对行为、数据、内存或其他代价，再决定是否接受。

测试条件可以逐步完善，但每个结论都要写清当时条件。

## 如何审阅“最小优化”

本次调整了缓存条目容量与命中顺序，保留已有字节预算、租约访问校验和会话结束清理；历史重建与保护门禁继续执行。

可推广的做法是：减少重复工作时，同时指出仍需执行的校验和依赖条件。固定数值只是本项目的实现参数。

## 可以复制的提问模板

```text
先给出有界测量方案：输入、状态、环境、候选、计时区间和调查上限。
分开报告各阶段耗时及读取/调用计数，保留全部样本。
提出一批最小优化，说明必须保持的行为、依赖条件及可能代价。
用相同输入比较前后候选，核对输出与状态；明确哪些设备和后端尚未测量。
```

## 小练习：找出一个不公平的比较

写一段比较：旧版使用一组大数据，新版使用另一组小数据。然后列出需要统一的条件，并重新设计可解释的对照。

- [ ] 能说清开始和结束计时的时刻。
- [ ] 能解释为什么保留每次运行数据。
- [ ] 能区分调用减少、耗时减少与用户感知改善。
- [ ] 能指出一项可能的内存、失效或一致性代价。

## 适用边界

吞吐、延迟、内存和数据安全可能互相影响。固定样本通过有助于判断这一批；扩大历史规模、改变设备或后端，需要新的证据。本项目仍保留大历史原生性能与移动端内存压力的边界。
