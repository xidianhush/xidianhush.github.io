## 需要分清的几个对象

- 工作区：磁盘上正在查看、编辑和构建的文件。
- 分支：指向提交历史的引用，会随提交推进。
- 提交：一份可定位的历史状态；未提交文件还需要另行记录。
- worktree：同一仓库的另一个检出目录，可以承载不同分支或状态。
- 构建产物：由源码和构建过程产生的运行文件。
- 实际安装：目标应用正在使用的那份运行文件及其状态。

版本号描述发行身份。核对能力和字节时，还需要提交、差异、构建及安装证据。

## 本次项目里的例子

同步体验来自 `dddf14a`，恢复能力来自 `6fdc757` 所在分支，另有已发布历史参考。两条功能线有共同祖先，但互不包含。工作区一度漏掉后继的一键体验，技术加固由此偏离了用户认可的界面。

后续明确活动工作区，记录固定来源，比较差异后整合两边能力。旧脏树及未跟踪内容保全，没有通过清空旧树消除混乱。

## 下次开工的最小核对

在确认的项目目录中，先做只读检查：

```bash
git status --short
git branch --show-current
git rev-parse HEAD
git worktree list
```

再让 AI 解释：哪份是活动树、哪些是参考树、已有修改属于什么、必要功能在哪个提交、测试或安装包对应什么来源。

处理分叉时，比较共同祖先和双方差异，明确要保留的行为，再决定合并方式。已有合适的隔离工作区可以继续使用。

## 可以复制的提问模板

```text
先不要修改文件。请核对当前工作区、分支、HEAD、已有差异及其他相关worktree。
指出本任务依赖的已验收能力分别来自哪里，哪些分支互不包含。
给出整合后需要保留的行为与回归范围。
保全独有未提交/未跟踪内容；需要移动或清理旧树时先说明可恢复方案。
```

## 小练习：写一张基线卡

为练习项目记录当前目录、分支、提交、已有修改、运行版本和必要能力。再找出一个“安装版本号相同，但仍需继续核对”的理由。

- [ ] 能解释自己现在改的是哪份文件。
- [ ] 能指出源码状态和实际安装之间还缺什么证据。
- [ ] 能说明旧工作树中哪些内容必须保留。

## 适用边界

分支和工作树数量多本身并不说明有问题；缺少职责、来源和回收记录会让判断困难。源代码历史、设备身份和私有运行状态需要分别管理，Git 提交不能覆盖所有这些对象。
