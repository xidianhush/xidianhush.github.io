# AI 辅助软件开发 - Workflow 总览

整理日期：2026-11-28｜状态：待审阅｜案例：Knowledge Map 1.0.0

==学习目标：能够把一个想法组织成 AI 可以实施、自己可以判断结果、以后可以继续维护的软件项目。==

这套笔记由本次 Obsidian 插件开发经历整理而来。项目事实按当时的代码、验收和发布记录描述；操作方法是供下次使用的建议；练习尚未执行。完成一次项目提供了学习材料，是否掌握还需要亲自尝试和解释。

## 一轮开发的工作流

目标与验收 → 开工基线 → 分批实施 → 技术验证 → 用户体验 → 最终交付 → 归档与复盘。

发现问题时回到“反馈—定位—修复—验证”的循环；新需求进入下一批。基线、证据和当前清单贯穿整个过程。

### 1. 先描述想得到的结果

说清使用者、使用场景、期望结果，以及已经满意、需要保留的行为。将抽象需求写成可以观察的动作和结果。

本次最关键的纠正是：用户满意现有一键同步，只希望少量提示更清楚。这个判断约束了后续方案。

本阶段产出：需求说明、保留范围、验收步骤。对应[[AI 开发技能 01 - 需求表达与验收标准]]。

### 2. 确认从什么现场开始

记录当前目录、分支、提交、已有修改，以及必须保留的功能来源。必要时核对实际安装文件。

本次两个分支分别有同步体验和恢复能力，相同版本号无法替代来源核对。对应[[AI 开发技能 03 - Git 工作区与开发基线]]。

### 3. 把工作拆成可以检查的小批次

每批写清：解决什么问题、改动范围、验证方式、完成条件。用户反馈和新决定及时更新到共同清单。

架构整理按职责逐步推进，回归检查随批次进行；重写和迁移需要独立理由。对应[[AI 开发技能 02 - 范围控制与分批推进]]。

### 4. 用证据判断技术结果

要求 AI 说明测试对象、实际命令或步骤、运行结果、覆盖范围和未测内容。需要评审的是改动与结论之间的证据关系。

静态检查、合成测试、磁盘故障测试、真实 Obsidian、第三方传输和用户体验各自回答不同问题。对应[[AI 开发技能 04 - 审阅 AI 输出与验证证据]]。

### 5. 由用户验收真实使用流程

在独立测试库里按照约定步骤操作，记录是否需要额外干预。不要为了让结果看起来正确而悄悄重建、重启或修改步骤。

本次“两端最终一致”和“已打开的画布自动更新”需要分别验收。异常进入[[AI 开发技能 05 - 缺陷反馈与系统定位]]。

### 6. 按需要测量性能

当有明确慢点时，先规定输入、环境、计时区间和调查上限，再分解耗时，做最小优化并复验行为。对应[[AI 开发技能 06 - 性能测量与最小优化]]。

### 7. 冻结并交付确切版本

核对源码、构建、实际安装和下载文件之间的关系；完成拟公开内容检查；按已有明确授权执行推送或发布，再回读结果。

本次三运行文件和无 `v` 的 tag 是本项目约定，其他项目应读各自规则。对应[[AI 开发技能 07 - 发布准备与交付核对]]。

### 8. 给下一轮留下可用入口

整理当前清单、源码基线、必要私有状态、恢复方法及未完成事项。把可推广的判断写成方法笔记或 agent skill。对应[[AI 开发技能 08 - 可恢复归档与经验复用]]。

## 人与 AI 怎样分工

用户负责产品目标、优先级、取舍和体验判断；AI 负责方案、实现、技术验证及证据整理。共同清单承接双方决定。

评审代码时，可以要求 AI 解释关键改动的输入、输出、状态变化和潜在回归。对代码不熟悉的地方继续追问；在关键路径逐步补齐阅读与判断能力。

## 下次开工可以直接用的提示

```text
先阅读项目当前清单和开发约定，确认我的最新目标。
报告当前工作区、分支、提交和已有修改，指出需要保留的行为。
把任务拆成少量能独立验证的批次，说明第一批的范围、验收方式和完成条件。
复用合适的既有隔离工作区；说明需要新增工作区的实际理由。
实际跑过的检查和未执行项分别记录；需要我做体验判断时给出简短步骤。
涉及发布、数据清理或日常数据写入时，核对本次已有授权。
```

## 如何审阅这套笔记

- [ ] 项目经过是否与自己的记忆一致？
- [ ] 哪张技能卡仍有看不懂的术语？
- [ ] 哪些步骤能照做，哪些还需要一个小例子？
- [ ] 哪些方法只适用于本项目，需要注明条件？
- [ ] 选择一项小练习，完成后再记录自己的掌握程度。
