## 本次项目里的例子

收尾涉及五个注册工作树、未提交修改、忽略资料、测试库、profile、设备回传包、截图和临时驱动。只看 Git 是否干净，无法知道这些材料是否存在。

实际整理采用稳妥方案：保全两脏树的差异及原始文件，核对恢复；整理历史文档和闲置文件；当前测试库与 profile 成对保留、复制并恢复验证。大型旧环境有路径和身份依赖，原位登记，未做重复全量镜像。

复核还发现文件摘要检查会漏掉空目录。补存目录清单后，配对环境的文件与目录都做了恢复核对。

## 下次怎样归档

1. 明确范围和保留规则，区分公共源码、私有状态、证据及可重建产物。
2. 盘点工作树、独有修改、未跟踪和忽略内容，记录目录关系。
3. 为材料决定原位、复制或核验后移动，并记录理由。
4. 保存清单、摘要、排除项、原路径与恢复办法；不覆盖已有目标。
5. 检查应用写入状态和来源稳定性，在新隔离目录做恢复演练。
6. 核对文件、目录及必要元数据，确认恢复副本不会误用原设备身份。
7. 给下一次开工留下总入口，明确哪些材料没有新的副本。

Git bundle 保存提交对象与引用；脏树差异、独有文件和私有运行状态仍需另行保全。索引说明材料去向，恢复演练检查副本是否能重建所需状态。

## 一个重要的事实边界

初末清册发现26个旧Python/Markdown条目的枚举信息与当前空文件状态不同，其所示mtime集中在11月9日，早于本轮。没有此前正文摘要，无法认定根因或恢复未知的更早内容。

后续通过逐文件实时状态核对，为两个先失败分组保全了当前字节。这个过程提醒：要区分目录信息、实际读取、当前副本和历史内容恢复。

## 怎样把经历提炼成 skill

保留会影响决策的规则：何时使用、先核对什么、需要哪些证据、什么情况下停止或交给用户。长案例按需引用。

本次产生了 `verified-development-delivery`：入口说明通用判断，参考文件分别讨论工作区与归档、发布证据和脱敏项目案例。固定版本、路径、测试数量和包结构属于案例参数。

## 可以复制的提问模板

```text
盘点本项目的源码、独有修改、忽略资料、测试库/profile、证据和交付包。
给每类材料记录处置、理由、摘要、排除项与恢复方式。
注册工作树和身份环境有依赖时原位保留；已移动项提供恢复映射并做隔离恢复。
把失败和未知历史内容单列，准确说明完成范围。
最后把可推广的决策规则写成短skill，项目参数放案例中。
```

## 小练习：恢复一个小样

在独立练习目录中准备几个合成文件和一个空目录，做归档，再恢复到新位置。检查内容、目录和需要保留的修改时间，记录遗漏及修正。

- [ ] 能找到原路径与归档路径。
- [ ] 能说明哪些材料没有进 Git。
- [ ] 能用恢复结果而非文件数量判断副本质量。
- [ ] 能写出一条适用于其他项目的规则。

## 适用边界

本次原位保留的环境仍依赖原位置；归档没有变成全盘镜像或跨盘灾难备份。复制测试库和profile后，也不能直接同时启动相同设备身份进行同步。
