# AI 开发技能 02 - 范围控制与分批推进

整理日期：2026-11-28｜状态：待审阅

入口：[[AI 辅助软件开发 - Workflow 总览]]｜案例：[[Knowledge Map 1.0.0 - AI 辅助开发复盘]]

==让每一批工作都有明确目的、有限改动和可检查的完成条件。==

## 什么时候用

任务涉及多个模块、AI 连续提出新建议、讨论跨越许多轮，或一次修改已经难以解释和回退时，用小批次维持方向与判断能力。

## 本次项目里的例子

工程加固期间，一份技术验证通过的候选使用了手动分步同步界面。用户指出已经有更满意的一键体验。后续先核对工作区和功能来源，保留工程加固，再按产品决定收敛界面。

这次纠正说明：批次结束时，需要同时检查技术结果和产品方向。后来文案、草稿审阅、接收更新、性能、README 与发布分别推进，各自留下证据。

## 下次怎样做

1. 用一句话写本批目标，例如“说明建图范围，不改变同步机制”。
2. 列出预计涉及的文件或模块，指出需要保持的契约。
3. 给出本批验证及完成条件，明确什么时候轮到用户验收。
4. 把发现的其他问题记为建议或下一批候选，说明是否阻塞当前目标。
5. 结束前更新当前清单：完成到哪里、证据在哪里、谁需要做下一步。

批次大小由风险和可审阅性决定。简单文字调整可以很小；持久化修复可能需要代码、回归和设备短验共同组成一个完整批次。

## 共同清单怎样写

每项至少记录：任务 ID、目标、状态、完成条件、证据及未完成内容。区分“建议”“已承诺”“技术通过”“待用户验收”“用户通过”。

新反馈更新对应条目；历史记录保留日期。读取旧 HANDOFF 时，要再核对当前清单与后续决定。

## 可以复制的提问模板

```text
请把这项工作拆成可独立检查的小批次。
每批说明目标、修改范围、保留行为、验证方式和完成条件。
先实施第一批；已授权的后续独立工作可以继续，不必重复询问是否开始。
新建议另列，涉及产品取舍时说明具体影响。
结束前更新对应任务状态，未执行的检查维持未执行。
```

## 小练习：评审一份计划

拿一个小功能的计划，逐项回答：这批为什么存在？完成后能观察到什么？失败会影响哪里？能否单独回退或保留现场？

- [ ] 能删去一项与本轮目标无关的工作。
- [ ] 能指出一个需要保持的行为。
- [ ] 能给“待用户验收”和“完成”写出不同条件。

## 适用边界

拆分不能割裂必要的依赖和验证。已有明确授权时重复审批会增加沟通成本；需要新的决定时，应提供具体可审阅结果和理由。

架构、类型和代码风格可以逐步改善。评审时关注职责、接口、状态变化与回归范围，再决定是否值得扩大整理。
